# 词页 CiYe 项目优化方案

> 本文档基于当前项目代码和说明文档阅读整理。目标是尽量彻底优化复习、遗忘、错词和学习进度逻辑，同时不改变当前项目外观和主要功能。

## 一、当前项目概况

词页 CiYe 是一个本地运行的背单词 Web 应用：

- 前端：Vue 3 + Vite
- 后端：Python 标准库 HTTP Server
- 数据库：SQLite
- 核心功能：词书管理、每日学习、艾宾浩斯遗忘曲线、拼写测试、错词本、收藏夹、统计、AI 助手
- 主要代码：
  - `server/app.py`：API 路由和大量业务逻辑
  - `server/db.py`：数据库连接、表结构、初始化
  - `server/ebbinghaus.py`：遗忘曲线计算
  - `src/components/StudyCard.vue`：学习卡片
  - `src/components/EbbinghausPanel.vue`：遗忘曲线面板
  - `src/components/SpellingTest.vue`：拼写测试

整体 UI 和功能框架已经比较完整，主要问题集中在学习调度内核和代码组织。

## 二、主要问题

### 1. 复习词可能被错误排除

`/api/today` 在生成今日队列时，会读取其他日期的 `studied_ids`，然后跳过这些单词。

这对“避免新词重复出现”可能有意义，但对复习词不合理。以前学过的词正是未来需要复习的词，如果因为出现在其他日期的 `studied_ids` 里被排除，就会导致复习队列漏词。

建议：

- 新词可以避免重复引入。
- 复习词不应该因为过去学过就被排除。
- 是否复习应由 `due_date` 或保持率决定。

### 2. `due_date` 被写入，但没有成为调度核心

数据库 `progress` 表有 `due_date` 字段，`/api/progress` 也会更新它。但今日队列和艾宾浩斯面板主要按：

```text
R = e^(-t/S)
R < 60%
```

来判断是否需要复习。

这会造成两套逻辑并存：

- 数据库里有下次复习日期。
- 实际调度却主要按保持率实时计算。

建议统一：

- 以 `due_date <= today` 作为是否进入复习队列的主判断。
- 保持率 `retention` 用于展示和排序。
- 每次反馈后重新计算 `due_date`。

### 3. 四个反馈按钮的实际差异不够

当前逻辑中：

- `known`：`S + 1.0`
- `easy`：`S + 1.0`

二者在记忆强度上没有差异，主要区别是 `easy` 直接设置为 `mastered`。

但前端文案写的是：

- 不认识：明天复习
- 模糊：2 天后复习
- 认识：4 天后复习
- 很熟：7 天后复习

实际算法并不稳定对应这些间隔，用户容易感觉反馈按钮“不真实”。

建议：

- `forgot`：降低记忆强度，短间隔复习。
- `vague`：小幅增强，1 天左右复习。
- `known`：中等增强，2-4 天复习。
- `easy`：大幅增强，4-7 天或更久复习。

### 4. `mastered` 状态语义不清

当前只要点击 `easy` 就可能进入 `mastered`。

但 `mastered` 的单词后续仍然可能因为保持率下降进入复习队列。这在算法上可以接受，但在用户理解上容易冲突：

- 统计里看起来已经掌握。
- 实际仍然需要复习。

建议：

- `mastered` 不应由一次 `easy` 决定。
- 可以要求连续多次高质量复习后才进入 `mastered`。
- `mastered` 表示“长期记忆稳定”，不是“永远不复习”。

### 5. 今日队列持久化方式偏脆

当前 `daily_session` 使用 JSON 数组保存：

- `word_ids`
- `studied_ids`

短期可用，但无法记录：

- 每个任务是新词还是复习
- 任务来源
- 排序原因
- 完成时间
- 是否是后续补入
- 当时的保持率

建议后续新增 `daily_session_items` 表，保留原 API 返回结构不变。

可设计为：

```sql
CREATE TABLE daily_session_items (
    user_id INTEGER NOT NULL,
    date TEXT NOT NULL,
    book_id INTEGER NOT NULL,
    word_id INTEGER NOT NULL,
    task_type TEXT NOT NULL,
    position INTEGER NOT NULL,
    status TEXT NOT NULL DEFAULT 'pending',
    source TEXT,
    retention_at_create REAL,
    created_at TEXT NOT NULL,
    completed_at TEXT,
    PRIMARY KEY(user_id, date, book_id, word_id)
);
```

### 6. 拼写测试没有反哺记忆模型

当前拼写测试答错只会：

```text
is_wrong = 1
```

不会：

- 写入学习事件
- 降低记忆强度
- 更新 `due_date`
- 提前加入复习
- 答对后帮助移出错词

建议：

- 拼写错误等价于一次 `forgot` 或专门的 `spell_wrong` 事件。
- 拼写正确等价于一次 `known` 或 `spell_correct` 事件。
- 错词连续答对若干次后，自动建议移出错词本。

### 7. 重置逻辑有误伤风险

`reset-today` 会把 `due_date = today` 的词也重置成 `new`。

这可能误伤以前学过、今天到期复习的词。

建议：

- 今日重置只重置当天新引入且当天学习的词。
- 不应把历史复习词重置为 `new`。
- 需要区分“今日新词”和“今日复习词”。

### 8. 部分单词可能没有 progress 记录

实际数据库抽样显示：

- `words`：7170
- `progress`：6992

说明存在部分单词没有对应学习进度记录。

建议：

- 每次进入词书、切换词书或生成今日队列前，补齐当前用户当前词书的 `progress`。
- 新增一个 `ensure_progress_for_book(uid, book_id)` 服务函数。

## 三、推荐优化路线

### 第一阶段：修复学习调度内核

优先级最高，且可以不改变外观。

目标：

- 今日队列稳定。
- 复习词不漏。
- `due_date` 和保持率逻辑统一。
- 新词和复习词边界清楚。

建议新增 `server/scheduler.py`：

```text
ensure_progress_for_book()
get_due_reviews()
get_new_words()
build_today_session()
refresh_today_session()
```

核心规则：

1. 先补齐当前用户当前词书的 `progress`。
2. 复习词：`status != 'new' AND due_date <= today`。
3. 新词：`status = 'new'`，按每日数量取。
4. 今日队列：复习词优先，新词在后。
5. 同一天刷新保持队列稳定。
6. 新到期复习词可以补入，但要有上限和稳定排序。

### 第二阶段：升级遗忘算法

不必完整实现复杂 FSRS，可以做一个 FSRS-lite / SM-2 改良版。

建议字段：

```sql
ALTER TABLE progress ADD COLUMN review_count INTEGER DEFAULT 0;
ALTER TABLE progress ADD COLUMN lapse_count INTEGER DEFAULT 0;
ALTER TABLE progress ADD COLUMN difficulty REAL DEFAULT 5.0;
ALTER TABLE progress ADD COLUMN last_grade TEXT;
ALTER TABLE progress ADD COLUMN first_seen_at TEXT;
```

推荐反馈效果：

| 反馈 | 含义 | 记忆强度变化 | 下次复习 |
|---|---|---|---|
| forgot | 完全不记得 | 明显降低 | 当天稍后或明天 |
| vague | 模糊 | 小幅增强 | 1 天左右 |
| known | 认识 | 中等增强 | 2-4 天 |
| easy | 很熟 | 大幅增强 | 4-7 天或更久 |

状态流转建议：

```text
new -> learning
learning -> reviewing
reviewing -> mastered
mastered -> reviewing   // 遗忘或答错时回退
```

如果不想改状态名，也可以继续使用：

```text
new / learning / mastered
```

但需要让 `mastered` 的进入条件更严格。

### 第三阶段：打通错词本和拼写测试

目标：

- 错词本不只是列表，而是复习系统的一部分。
- 拼写测试会影响记忆强度和复习安排。

建议：

- 拼错时：
  - `is_wrong = 1`
  - `lapse_count + 1`
  - 写入 `events`
  - 降低 `memory_strength`
  - 提前 `due_date`
- 拼对时：
  - 写入 `events`
  - 增加正确次数
  - 可轻微提高记忆强度
  - 连续答对后可自动移出错词本

测试范围也建议调整：

- 今日学过的词：只抽 `studied_ids` 或已完成任务，不抽今日队列全部。
- 全部词：默认只抽已学词，不抽完全 `new` 的词。
- 错词本：优先抽 `is_wrong = 1` 的词。

### 第四阶段：整理后端代码结构

当前 `server/app.py` 过大，建议逐步拆分。

可拆为：

```text
server/
  app.py                # 路由入口，保持 API 路径不变
  db.py
  auth.py
  dict.py
  ebbinghaus.py
  scheduler.py          # 今日队列和复习调度
  progress_service.py   # 学习反馈、记忆强度、事件记录
  book_service.py       # 词书导入、编辑、删除
  test_service.py       # 拼写测试、错词本联动
```

原则：

- 不改变前端 API 路径。
- 每次只搬一类逻辑。
- 每搬一次做手动验证。

## 四、可以新增的功能

以下功能都可以在不改变主外观的基础上增加。

### 1. 撤销刚才的反馈

学习时点错按钮很常见。可以保存最近一次反馈事件，允许撤销。

需要：

- 删除最近事件或标记为撤销。
- 回滚 progress 的关键字段。
- 从 `studied_ids` 中移除对应词。

### 2. 未来 7 天复习预测

在遗忘曲线或今日计划区域显示：

```text
明天 23 个
后天 18 个
3 天后 41 个
```

帮助用户理解学习负荷。

### 3. 学习负荷保护

如果当天复习词过多，自动减少新词。

示例：

```text
如果复习词 > 80，则今日新词减半。
如果复习词 > 150，则暂停新词。
```

### 4. 难词/顽固词标签

当一个词多次 `forgot` 或拼写错误，可以自动标记为难词。

用途：

- 错词本中高亮。
- 拼写测试优先抽取。
- AI 助手可针对难词生成记忆法。

### 5. 单词详情学习历史

点击单词后展示：

- 第一次学习时间
- 最近一次复习时间
- 下次复习时间
- 答对次数
- 答错次数
- 记忆强度曲线

### 6. 导出和备份

本地 SQLite 项目很适合做：

- 导出词书 CSV
- 导出学习记录 JSON
- 导出错词本
- 一键备份 `data/app.db`

### 7. 导入质量报告

导入词书时提示：

- 重复词
- 空释义
- 疑似中文乱码
- 疑似模板例句
- 无法识别的行

## 五、建议实施顺序

### P0：必须先做

1. 修复 `/api/today` 中复习词被过去 `studied_ids` 排除的问题。
2. 统一 `due_date` 和保持率逻辑。
3. 生成今日队列前补齐缺失 `progress`。
4. 修复 `reset-today` 对历史复习词的误伤风险。

### P1：核心体验优化

1. 调整四个反馈按钮对应的记忆强度和复习间隔。
2. 改进 `mastered` 判定。
3. 拼写测试接入学习事件和记忆模型。
4. 错词本支持自动恢复和专项复习。

### P2：结构优化

1. 拆出 `scheduler.py`。
2. 拆出 `progress_service.py`。
3. 拆出 `test_service.py`。
4. 给关键算法加最小测试脚本。

### P3：增强功能

1. 未来复习预测。
2. 撤销反馈。
3. 学习负荷保护。
4. 难词标签。
5. 导出和备份。

## 六、优先推荐的第一步改造

建议先只做一个小闭环：

```text
修复今日队列生成 + 统一复习判断 + 补齐 progress
```

这一阶段不需要改 UI，不需要动前端外观，也不需要改主要功能入口。

完成后，用户会直接感受到：

- 该复习的词会稳定出现。
- 新词数量更符合设置。
- 今日队列刷新后不乱跳。
- 遗忘曲线面板和今日学习的复习数量更一致。
